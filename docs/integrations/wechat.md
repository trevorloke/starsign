# WeChat (Official Account / 公众号)

Connector `wechat` · networks `["wechat"]` · `packages/connectors/src/wechat.ts` (+ `wechat-crypto.ts`) · factory `createWeChatConnectors(env)`

Uses the official WeChat Official Account platform API (`api.weixin.qq.com`) only. No personal-account automation, no web-client scraping, no itchat/wechaty "puppets".

## What Starsign can and cannot see
- **Starsign sees the messages people send to your Official Account**: text, plus short summaries of images, voice messages (with WeChat's speech-to-text when it is there), videos, locations and shared links. It also sees new followers. It can answer a person by customer service message for 48 hours after their last message.
- **Starsign cannot see personal chats or WeChat groups (群聊).** No official WeChat API lets anyone read personal chats or group chats, and Starsign will not pretend otherwise. The tools that claim to do this ("puppet" / hook / web-protocol bots that log in as a personal WeChat) are unofficial. WeChat detects them and **restricts or permanently bans the accounts** that use them. Starsign does not use them.
- **The official route to monitor groups is WeCom (企业微信)**, not WeChat. A business that runs its customer groups as WeCom **customer groups (客户群)** can, with the paid **会话内容存档 (conversation content archive)** add-on and the members' consent notices, read those group messages through WeCom's official API. Starsign's `wecom` connector (docs/integrations/wecom.md) does not read customer groups; it handles WeChat Customer Service (微信客服) chats and posting into internal WeCom groups through group bots. Even the archive covers only groups created by your WeCom staff, never arbitrary WeChat groups.
- When Starsign publishes, it creates an article on your account (a draft that is then published). It sees the article's id and link; for articles sent to followers by mass send it can read read counts and shares a day later.
- Starsign does not see comments under your articles (留言 has no general API for self-developed accounts), Moments (朋友圈), Channels (视频号), or anything about people beyond the opaque openid WeChat gives for each follower.

## What works
- **Connect** (`connectMethod: "api_key"`): inputs `appId` (AppID), `appSecret` (secret), `originalId` (the account's original ID `gh_…`, which is the `ToUserName` of every message), `token` (secret; the Token you typed in the server configuration), `encodingAesKey` (secret; 43 characters, needed for safe mode), `author` (optional; the author shown under articles, up to 16 characters) and `broadcast` (optional, "Send to followers (uses your mass-send quota)": `yes` or empty). EncodingAESKey is optional: leave it empty when the account uses plaintext mode. `connectWithInputs` validates formats (without echoing values), then calls `POST /cgi-bin/stable_token` to prove the AppID/AppSecret and that the server's IP is allowed. Account externalId and handle = original ID; displayName is null (self-developed accounts have no API returning their own nickname). Auth blob: `{ appId, appSecret, originalId, token, encodingAesKey? }`. Config: `{ appId, mode: "safe" | "plaintext", webhookUrl, author?, broadcast? }` where `webhookUrl` is the exact server URL to paste into WeChat.
- **Access token**: `stable_token` (normal mode), cached in memory per AppID with its expiry (~7200 s) and renewed 5 minutes early; concurrent requests share one fetch. On 40001/40014/42001 the cache is dropped and the call retried once with a fresh token; if `stable_token` hands back the same rejected token, the connector asks once with `force_refresh: true` (WeChat limits forced refreshes to about 20 a day).
- **Webhooks** (per-account Token and AES key):
  - `route`: `?account=<gh id>` from the URL; for POST bodies, falls back to the XML `ToUserName` (present in plaintext and in the encrypted envelope).
  - `challengeAccount` (GET server check): `signature == sha1(sort([token, timestamp, nonce]).join(""))` compared in constant time → returns `echostr`.
  - `verifyAccount`: plaintext mode checks the same `signature`; safe/compatible mode (`encrypt_type=aes` or an `Encrypt` element) checks `msg_signature == sha1(sort([token, timestamp, nonce, Encrypt]))`. Timestamps more than 5 minutes off are rejected (replay protection).
  - `decodeAccount`: parses the XML (own small parser: CDATA, entities, nested elements; no dependency) and, in safe mode, decrypts `Encrypt`: AES-256-CBC, key = base64(EncodingAESKey + "="), IV = key[0..16], PKCS#7 padding to 32 bytes, plaintext = 16 random bytes + 4-byte big-endian length + XML + AppID; the trailing AppID must equal the account's AppID.
  - `ack`: plain text `success` (WeChat shows "该公众号暂时无法提供服务" to the person for any other non-XML body).
  - `parse`: `text` → `dm`; `image` → `[image] <PicUrl>`; `voice` → `[voice] <Recognition>` or `[voice message]`; `video`/`shortvideo` → `[video]`; `location` → `[location] <Label> (x, y)`; `link` → `[link] <Title> <Description> <Url>`; other types → `[<type>]`. Event `subscribe` → `follow` (QR scene noted); `unsubscribe` and other events are ignored. conversation `{ id: openid, type: "direct" }`, authorHandle = openid, authorName null, externalId `<openid>:<MsgId>` (or `<openid>:<CreateTime>` without MsgId), occurredAt from CreateTime, accountExternalId = ToUserName (so a delivery verified with one account's Token cannot inject items into another account).
- **reply**: customer service message `POST /cgi-bin/message/custom/send` `{ touser: openid, msgtype: "text", text: { content } }` with the openid taken from the parent's external id. Idempotent in-process. The API returns no message id, so the reply's externalId is `<openid>:reply:<idempotencyKey>`. 45015 → `rejected` ("WeChat only allows replies within 48 hours of the person's last message, or they unfollowed").
- **Publish an article (图文)** — capability `publish: true`, `kinds: ["post"]`:
  - **Title**: `options.title`, else the first line of the text (which then leaves the body). Required, at most 64 characters.
  - **Cover** (required): the first attached image, uploaded as permanent image material `POST /cgi-bin/material/add_material?type=image` (multipart field `media`, up to 10 MB) → `media_id` used as `thumb_media_id`. A post without an image fails validation (`media_required`).
  - **Body**: the text rendered by `html.ts` `textToHtml` (paragraphs, headings, lists, quotes, bold/italic/code, http(s) links; everything else HTML-escaped, so no script/iframe/style can be injected), then every attached image as a `<figure><img>` pointing at the WeChat URL returned by `POST /cgi-bin/media/uploadimg` (WeChat refuses external image URLs inside articles). uploadimg takes JPG/PNG up to 1 MB: larger or other images are used as the cover only and listed in the result's `raw.images_not_in_body`. `options.link` is appended as a link paragraph and set as `content_source_url` (阅读原文).
  - **Digest**: the first paragraph of the body, up to 120 characters. **Author**: the account's `author` setting when set. Comments are off (`need_open_comment: 0`).
  - **Flow**: `POST /cgi-bin/draft/add` `{ articles: [{ article_type: "news", title, author?, digest, content, content_source_url?, thumb_media_id, need_open_comment: 0, only_fans_can_comment: 0 }] }` → draft `media_id`; then `POST /cgi-bin/freepublish/submit` `{ media_id }` → `publish_id`; then `POST /cgi-bin/freepublish/get` `{ publish_id }` up to 10 times, 3 s apart. `publish_status` 0 → success: externalId = `article_id`, url = `article_detail.item[0].article_url`. 1 (still publishing after the wait) → `unknown`, retryable; the job is remembered per idempotency key, so the retry polls the same `publish_id` instead of submitting again. 2 → rejected "original-content (原创) check failed", 3 → rejected "general failure" (`fail_idx` in the error cause), 4 → rejected "platform review failed", 5 → rejected "deleted by the account after publishing", 6 → rejected "banned by WeChat after publishing".
  - **Freepublish does not push**: the article appears on the account's profile/article list and can be shared, but followers get **no notification** and it does not show in their chat list. That is the difference from a mass send.
  - **Send to followers** (`broadcast: yes` at connect): instead of freepublish, `POST /cgi-bin/message/mass/sendall` `{ filter: { is_to_all: true }, mpnews: { media_id: <draft media_id> }, msgtype: "mpnews", send_ignore_reprint: 0, clientmsgid }`, where `clientmsgid` (32 hex chars) is derived from the idempotency key so WeChat itself refuses a second send of the same post (45065). Result: externalId `mass:<msg_data_id>:<China date>`, url null (the send is asynchronous). Mass send needs a **verified** account and uses the **mass-send quota** (a few per month for service accounts, one per day for subscription accounts); 45028 (no quota left) → rejected with "turn off Send to followers or wait for the quota to reset"; 45066 (retried too fast) → rate_limit retryable; 48001 → rejected (not authorized). Accounts with "API mass-send protection" on need an administrator to confirm each send in WeChat within 30 minutes, or it fails.
  - Idempotent in-process (`IdempotencyCache`).
  - `validate`: title present and ≤ 64; at least one image; images only (no video/GIF/document); cover ≤ 10 MB; no threads; kind `post` only; body HTML estimated under 20,000 characters.
- **Per-article metrics** (`fetchMetrics`, best effort): for mass-sent articles (`mass:<msg_data_id>:<date>`), `POST /datacube/getarticletotal` with `begin_date = end_date = <send date>`; rows whose `msgid` starts with `<msg_data_id>_` are summed, taking the latest `details` entry (running totals): `int_page_read_count` → `impressions`, `int_page_read_user` → `reach`, `share_count` → `shares`, `add_to_fav_count` → `saves`. Data appears the day after sending and covers up to 7 days; a refused date (not available yet) or a missing permission returns nothing. **Freepublish articles get no metrics**: getarticletotal counts mass sends only, and WeChat marks it as soon to be retired in favour of newer statistics APIs whose per-article shape was not confirmed for this build.
- **Account metrics**: `followers_total` from `GET /cgi-bin/user/get` (`total`). If the account is not permitted (48001/50001/50002) nothing is returned.
- **Not supported**: `moderate`, `fetchActivity` (returns `[]`: WeChat only pushes; there is no API to read messages back), video articles, multi-article sends (one article per post).
- **Errors**: WeChat answers HTTP 200 with `errcode`. -1 → network (retryable); 40164 → rejected with "add this server's outbound IP to the API IP whitelist" (kept `rejected` so core shows the message and does not ask to reconnect); 89501/89503 → rejected (admin must approve the IP); 40001/40014/42001 → auth (after one refresh); 40013/40125/41002/41004/40243 → auth (AppID/AppSecret rejected or frozen); 45009/45011 → rate_limit (retryable); 45015, 45047, 43004, 48001, 40003 → rejected with explanations. Publishing: 40005/40113 (image type), 40009 (image too large), 40007 (bad media id), 53503 (draft failed the publish check), 53504/53505 (draft must be opened/saved in the console), 45028/45065 (mass-send quota / already sent) → rejected; 45066 → rate_limit. AppSecret, Token, EncodingAESKey and access tokens are never put in errors (error text is scrubbed; URLs are never included).

## Setup
1. Have an Official Account. For replies, it must be a **verified service account (已认证服务号)**: the customer service message API is not available to unverified accounts or (in most cases) subscription accounts. Publishing (draft + freepublish) and the material upload APIs need the draft/publish permissions, which verified accounts have; mass send needs a verified account.
2. In the **WeChat Developer Platform** (微信开发者平台, developers.weixin.qq.com/platform; older accounts: mp.weixin.qq.com → 设置与开发 → 基本配置), open the Official Account and:
   - copy the **AppID**, enable/reset the **AppSecret** (it is shown once);
   - in **API IP 白名单**, add the **outbound IP(s)** of the Starsign server(s) that call `api.weixin.qq.com` (single IPs or ranges; no ports). Wait a few minutes.
   - find the **original ID (原始ID, gh_…)** in the account information.
3. In Starsign, connect WeChat with AppID, AppSecret, original ID, a Token you choose (3–32 letters/digits) and, for safe mode, an EncodingAESKey (generate it in the next step first; leave it empty for plaintext mode).
4. Back in the platform's **消息推送 / 服务器配置**: URL = `${STARSIGN_PUBLIC_URL}/webhooks/wechat?account=<gh_id>` (shown in the account's config as `webhookUrl`), Token = the same Token, EncodingAESKey = the same key, 消息加解密方式 = **安全模式** (recommended) or 明文模式. Submit: WeChat calls the URL with `echostr`, Starsign answers if the Token matches. Then **enable** the server configuration. Note: enabling it turns off the platform's own auto-replies and custom menu configured in the web console.
- Redirect URI: none (not OAuth).
- Webhook URL: `${STARSIGN_PUBLIC_URL}/webhooks/wechat?account=<gh_id>`. Must be a public domain on port 80/443 (http or https); intranet hosts and IP addresses are refused by WeChat.
- Env vars: `STARSIGN_PUBLIC_URL`; optional `WECHAT_API_BASE` (e.g. `https://api2.weixin.qq.com` disaster-recovery domain, or a regional `sh.`/`sz.`/`hk.api.weixin.qq.com`).

## Review and access requirements
- **Verification (微信认证)** of the service account (annual fee, business documents; usually a few days to two weeks) unlocks the customer service message API and the user list. Before verification, Starsign still receives messages (the server configuration works for every account) but cannot reply or count followers.
- No app review by WeChat beyond that; the API IP whitelist and AppSecret are controlled by the account's administrator (who confirms changes by scanning with WeChat).
- **Mainland-China realities**: Official Accounts are registered by a mainland entity (or an overseas entity through the overseas registration process). The webhook must answer within **5 seconds** from WeChat's servers in China, so the Starsign endpoint should be reachable and fast from mainland China (a mainland or Hong Kong region helps; a server in mainland China needs an **ICP filing (备案)** for its domain). Starsign's outbound calls to `api.weixin.qq.com` must come from fixed IPs on the whitelist: serverless or autoscaled hosts with changing egress IPs need a NAT/egress gateway with static IPs. `api.weixin.qq.com` is reachable globally but latency from outside China varies; `api2.weixin.qq.com` is the fallback domain.

## Limits and quotas
- Access token: valid up to 7200 s; `stable_token` force refresh ~20/day with ≥30 s between calls; daily call quotas per API (e.g. `stable_token`), errcode 45009 when exceeded.
- Customer service messages: only within **48 hours** of the person's last interaction (message, menu click, follow, scan…); no per-message quota inside the window, but a per-user downlink cap (45047) applies.
- User list: up to 10,000 openids per `user/get` page (Starsign reads only `total`).
- Messages: WeChat retries a webhook delivery 3 times if no answer within 5 s; core deduplicates on `(network, externalId)`.
- Text content: `NETWORK_LIMITS.wechat.maxText` is 600 and `maxMedia` 1 in Starsign's shared limits, which also bound articles today (a 600-character article with one image). Articles themselves allow content under 20,000 characters / 1 MB; raising the shared limit is a schema change outside this connector.
- Articles: title ≤ 64, digest ≤ 120 (WeChat auto-fills it when empty), author ≤ 16; body images JPG/PNG ≤ 1 MB (uploadimg); cover ≤ 10 MB (permanent material). Permanent material has a total cap (100,000 images) and each publish adds one cover.
- Freepublish: no push quota. Mass send: limited per month/day by account type (check the remaining quota in the console); `send_ignore_reprint: 0` stops the send if WeChat judges the article a reprint.
- Metrics: datacube data has a one-day delay and covers 7 days after a mass send.

## Questions for the owner
- Which Official Account(s): service account or subscription account, and is it **verified**? (Replies need a verified service account.)
- What are the **static outbound IPs** of the Starsign servers to add to the API IP whitelist?
- Safe mode or plaintext mode? (Safe mode recommended.)
- Is anything else already using this account's server configuration (another platform's auto-replies, a menu, a CRM)? Only one server URL can be active; Starsign would replace it, and enabling it disables the console's auto-replies and menu.
- Where will Starsign be hosted for China traffic (5-second webhook answer from mainland), and is an ICP filing in place if hosted in mainland China?
- Do you need group monitoring? If yes, are your customer groups run in **WeCom**, and would you buy 会话内容存档 for a later WeCom connector?
- Should articles go out as **freepublish** (no push, no quota) or **mass send** to followers (push, monthly/daily quota)? Is "API mass-send protection" on (an admin then confirms each send)?
- Which author name should appear under articles, and should comments be open?
- Do you want the shared WeChat limits raised (text length, number of images) so longer articles with several images pass Starsign's generic validation?
